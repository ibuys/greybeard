I'm continuing work on Greybeard, my small Nagios-inspired monitoring engine written in Go.

We recently implemented state confirmation using consecutive observations, and then did a focused cleanup/review pass. I'm uploading the current Go source again; please treat the uploaded code as authoritative.

Current state-confirmation behavior:

* Checks execute external plugins/scripts and interpret exit codes 0–3 as OK/WARNING/CRITICAL/UNKNOWN.
* PostgreSQL stores every observation and the durable confirmed state.
* `attempts` is a state-confirmation threshold, not a retry count.
* Any state change requires N consecutive observations of the same new state.
* Recovery uses the same confirmation rule.
* The first-ever observation establishes the initial confirmed state immediately.
* Candidate states are memory-only and deliberately lost on restart.
* Confirmed states are loaded from PostgreSQL at startup.
* Every observation is persisted.
* Only confirmed state changes update the durable `states` table.
* Flapping detection and actions/notifications are still out of scope.

The architecture is:

observation → state confirmation decision → durable confirmed state → actions later

`StateTracker` owns confirmation policy. PostgreSQL persistence does not decide state transitions.

> Greybeard does not persist or recover scheduler state. On every startup, it reads configuration, verifies database availability, loads persisted monitoring state, and schedules all configured checks from scratch. Missed check executions are not replayed.

> PostgreSQL is required runtime infrastructure for Greybeard. If Greybeard cannot read or write its persistent state, it exits rather than continuing in a degraded mode.
